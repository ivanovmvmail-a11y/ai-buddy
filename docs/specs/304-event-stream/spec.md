# 304 — Поток событий в Apache Kafka

Статус: **реализована (спецификация и код в одном PR, 14.11)** · Автор: Claude · Основание: ТЗ («в инфраструктуре
Авито уже есть Clickstream, RPC/Apache Kafka — рекомендуем использовать эти компоненты»), полная проверка 14.11
(«Kafka есть только на схеме»), решение Миши 14.11 — добавить.

## 1. Зачем
События продукта (стажёр спросил, заявка создана, пункт закрыт, задание сдано) в Авито попали бы в Clickstream через
Kafka. В прототипе они писались только в таблицу `events` для Grafana. Теперь те же события уходят и в настоящий
брокер Kafka — чтобы при внедрении не дописывать отправку, а только поменять адрес брокера.

## 2. Роли
Фоновый процесс, пользователь его не видит. Состояние потока (`GET /events/stream`) может прочитать любая вошедшая
роль: в ответе только счётчики.

## 3. Поведение
- **Таблица `events` остаётся источником правды** (спека 302): Grafana и метрики читают её, как раньше.
- После **успешной** записи операции сервис отдаёт её новые события в поток (`app/mcp_server/storage.py`,
  `DemoStore`). Операция отменена (ошибка, отказ по правам) — её события в Kafka не попадают.
- Топик — `KAFKA_TOPIC` (по умолчанию `ai-buddy.events`), ключ сообщения — `user_id` (порядок событий одного
  пользователя сохраняется). Сообщение — JSON в формате Clickstream-события:
  `{"event", "ts", "user_id", "role", "team", "payload", "source": "ai-buddy"}` — тот же состав, что в таблице.
- **Текстов вопросов и ответов в событиях нет** (как и в таблице): только тема, флаги, идентификаторы.
- События шлют оба процесса: backend (вопросы, оценки, проверка заданий) и служба `mcp` (заявки, статусы пунктов).

## 4. Kafka не может помешать работе
- Отправка — в фоновом потоке через очередь в памяти (до 1000 событий): запрос пользователя брокера не ждёт.
- Брокер недоступен: три попытки с паузой, затем событие считается пропущенным для Kafka (в таблице оно есть).
  Очередь переполнена — новые события для Kafka пропускаются. Исключения наружу не выходят.
- В `docker-compose.yml` от службы `kafka` никто не зависит: остальные службы стартуют и работают без неё.
- `KAFKA_BOOTSTRAP` пуст (тесты, облако без Kafka) — модуль ничего не делает.

## 5. HTTP
`GET /events/stream` → `{"enabled": bool, "topic": str | null, "connected": bool, "queued": int, "sent": int, "dropped": int}` —
счётчики этого процесса backend.

## 6. Как увидеть
```bash
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic ai-buddy.events --from-beginning --timeout-ms 5000
```

## 7. Критерии приёмки
| № | Критерий | Тест (`backend/tests/test_event_stream.py`) |
|---|---|---|
| AC-1 | Без `KAFKA_BOOTSTRAP` поток выключен и ничего не делает | `test_disabled_without_bootstrap` |
| AC-2 | Событие уходит в топик с ключом `user_id` в формате Clickstream | `test_event_goes_to_topic_in_clickstream_shape` |
| AC-3 | Брокер недоступен: повтор, затем пропуск без исключений; продюсер не создаётся — то же | `test_broker_down_retries_then_drops_without_raising`, `test_producer_cannot_be_created` |
| AC-4 | Переполненная очередь не блокирует, а пропускает | `test_full_queue_drops_instead_of_blocking` |
| AC-5 | В Kafka попадают только события успешно записанных операций | `test_store_publishes_only_committed_events` |
| AC-6 | Состояние потока по HTTP; без пользователя — 401 | `test_status_http` |

Проверено вживую 14.11 в чистом Docker: вопрос в чате, заявка на доступ и закрытие пункта дали 7 событий в топике
от двух служб; `docker compose up --wait` — все 7 служб `healthy`.

## 8. Что вне прототипа
Гарантия доставки «ровно один раз» (в Авито — outbox или CDC из таблицы событий), схемы сообщений (Schema Registry),
потребители. Kafka здесь одна, без репликации, в режиме KRaft.
