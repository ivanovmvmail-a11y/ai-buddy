## 1. Зачем
Жюри и Авито нужно видеть пользу вживую: сколько вопросов бот закрыл сам, сколько ответов с источником,
что стажёры спрашивают чаще и на что в документах нет ответа (сигнал наставнику дописать документ).
Золотой набор (004) доказывает качество на контрольных вопросах; события показывают реальное использование.

## 2. Пользователи и роли
| Роль | Что видит в метриках |
|---|---|
| Наставник | по своим стажёрам: частые темы, вопросы без ответа по темам, оценки ответов |
| Руководитель | то же по стажёрам своей команды |
| Куратор | по всем стажёрам |
| Стажёр, HR BP | метрик нет (`404`, как для чужих данных) |

**Только темы и количество — без текстов вопросов и без имён** (SPEC 5): метрики не становятся слежкой за стажёром.

## 3. Сценарий
1. Аня спрашивает бота → событие `question_answered`: тема (по ключевым словам), был ли источник, был ли отказ,
   «нет в базе», какие инструменты, время ответа. **Текст вопроса не сохраняется.**
2. Под ответом бота — «Полезно» / «Не полезно» → событие `answer_feedback`.
3. Пётр видит в карточке Ани «Частые темы: git — 3, доступы — 2» и «Без ответа: окружение — 1».
4. Куратор/руководитель видят сводку: вопросы, закрыто без человека, доля с источником, оценки, время ответа.

## 4. Поведение агента
Агент только записывает событие после ответа; на ответ это не влияет. Сбой записи события не ломает чат.

## 5. Данные
Таблица `events` (миграция онбординга, спека 101) через `app.mcp_server.events.log_event(SYSTEM_ACTOR, …)`;
кто спрашивал — в `payload` (`user_id`, `role`, `team`, `intern_id` для стажёра).

| Событие | payload |
|---|---|
| `question_answered` | `answer_id, user_id, role, team, intern_id?, topic, with_source, refused, not_in_base, tools[], drafts, latency_ms` |
| `answer_feedback` | `answer_id, user_id, role, team, intern_id?, useful` |

Темы: `git` (репозиторий, pull request, ревью, ветки), `access` (доступы, заявки), `environment` (стенд,
песочница, запуск, пайплайн, ноутбук), `tasks` (задачи, бэклог, Jira), `plan` (план, следующий шаг),
`people` (к кому идти, наставник, встреча), `hr` (отпуск, больничный, отгул), `other`.

## 6. API
- `POST /chat` → дополнительно `answer_id` (для оценки).
- `POST /feedback` `{answer_id, useful}` → `204`. Оценить можно только свой ответ.
- `GET /metrics?intern_id=` → сводка в пределах прав (см. раздел 2).

## 7. Критерии приёмки
- **AC-1.** После ответа бота записано `question_answered` с темой и флагами, без текста вопроса.
- **AC-2.** «Полезно/Не полезно» записывает `answer_feedback`; чужой `answer_id` → `404`.
- **AC-3.** Наставник получает метрики только своих стажёров, руководитель — своей команды, куратор — всех; стажёр и HR BP — `404`.
- **AC-4.** Метрики: вопросов, закрыто без человека (ответ с источником или по данным сервиса, не «нет в базе», не отказ), доля с источником, «нет в базе» по темам, доля «полезно», среднее время ответа, частые темы.
- **AC-5.** Сбой записи события не ломает ответ чата.
- **AC-6.** Интерфейс: кнопки оценки под ответами модели; в карточке наставника — частые темы и темы без ответа.
