# 303 — Единые уведомления: план реализации

## 1. Подход
Расширяем существующие напоминания (спека 301), а не заводим новый канал: у `Reminder` появляются `kind`, `action`
(подпись и цель перехода) и ссылки на объект. Все сервисы создают уведомления одной функцией `notify` с ключом
повода — так дубли невозможны (один повод — одно активное уведомление). Интерфейс по `kind` выбирает одну главную
кнопку и куда она ведёт; текст приходит с сервера.

## 2. Что меняется
| Часть | Файлы / модули | Чья зона |
|---|---|---|
| Имитации сервисов | `backend/app/mcp_server/notifications.py`, вызовы `notify` в `hiring.py`, `checklist.py`, `absence.py` | Codex (#70) |
| База | `supabase/migrations/20261111163000_notification_links.sql` | Codex |

| Контракт | `docs/API.md`, раздел «Напоминания и уведомления — новые типы» | Claude (#65) |

## 3. Данные и контракты
```json
{ "id": "rem_…", "user_id": "intern-anya", "kind": "skill_changed",
  "text": "Наставник отметил: Git — знаком. План обновился",
  "action": { "label": "Открыть план", "target": "plan" },
  "plan_item_id": null, "request_id": null, "suggestion_id": null, "absence_request_id": null,
  "status": "active", "created_day": 4, "snooze_until_day": null }
```

## 4. Проверка
Сервисные тесты на каждый повод, дедупликацию и перезапуск PostgreSQL; тесты интерфейса на кнопку и переход. Вживую —
шаги 5–7 маршрута README (Пётр → Ольга → Аня).

## 5. Риски и запасной вариант
Много поводов → шум. Ограничение: одно активное уведомление на повод, факты без «Напомнить завтра», отказы стажёру не
показываются.

## 6. Что заменяется при внедрении в Авито
Колокольчик — корпоративный мессенджер или центр уведомлений Авито; `notify` становится вызовом его API. Поводы и тексты
не меняются.
