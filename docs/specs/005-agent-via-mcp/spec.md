# 005 — Агент ходит к корпоративным сервисам по MCP

Статус: **реализована (спецификация и код в одном PR, 13.11)** · Автор: Claude · Основание: ТЗ («оформлять действия через
MCP», критерий «Внедряемость и интеграции» 30%), проверки 12–13.11 («веб-агент вызывает сервисы напрямую, а не по MCP»).

## 1. Зачем
MCP-сервер с имитациями сервисов (`app/mcp_server/server.py`, 20 инструментов, права внутри) был, но агент чата
вызывал те же функции в одном процессе мимо протокола. Эксперт, читающий код, видел: «MCP есть, но агент им не
пользуется». Нужно, чтобы путь «вопрос → модель → инструмент → корпоративный сервис» шёл по протоколу MCP, а замена
имитаций на настоящие MCP-серверы Авито была заменой транспорта, а не переписыванием агента.

## 2. Роли
Все роли чата. Права не меняются: проверка до вызова (`tools.py`, спека 001) и внутри MCP-сервера.

## 3. Поведение
- Шлюз `app/agent/services.py` — единственное место, откуда инструменты агента (`onboarding_tools.py`) и сводка для
  промпта (`plan_context`) обращаются к сервисам.
- `AGENT_SERVICES=mcp` (в Docker-образе по умолчанию): на вызов — MCP-сессия от имени вошедшего пользователя
  (`create_server(user.id)` — пользователь задаётся доверенной стороной, не моделью), `initialize` → `tools/call` →
  `structuredContent` → модель сервиса (`Plan`, `AccessRequest`, …). Дальше ответ строится так же, как при прямом вызове.
- `AGENT_SERVICES=direct` (по умолчанию без Docker, тесты) — прямой вызов функций сервиса.
- Ошибки протокола → доменные ошибки: «Не найдено» → `NotFound` (чужое неотличимо от отсутствующего), тексты отказов
  сервисов → `Forbidden`, ошибка схемы аргументов → `InvalidArguments`, «Сервис временно недоступен» → сбой, остальное →
  `Conflict` с текстом. Модель видит тот же ответ, что и при прямом вызове.
- Через MCP: план, отметка пункта, ресурсы и заявки на доступ, решение по заявке, карта навыков, список отгулов.
  Не через MCP, намеренно: **подтверждение** отгула и напоминание по просьбе — доверенный вызов после кнопки человека
  (у MCP-сервера нет инструмента «подтвердить»: модель не может подтвердить действие сама), демо-часы.

## 3a. По сети (изменение 13.11)
- В Docker MCP-сервер — отдельная служба `mcp`: `python -m app.mcp_server.http_server`, Streamable HTTP (`POST /mcp`,
  без состояния, JSON-ответы), `GET /health`. Порт наружу не открыт.
- Доверие: `Authorization: Bearer <MCP_SERVICE_TOKEN>` (иначе 401) и `X-AI-Buddy-User: <id>` (неизвестный — 403).
  Пользователя ставит backend по входу; у инструментов нет аргумента «от имени кого», модель его не выбирает.
- Backend: `AGENT_SERVICES=mcp` + `MCP_URL=http://mcp:8001/mcp` → HTTP-клиент SDK. Без `MCP_URL` — транспорт в памяти.

## 4. Что заменяется при внедрении
`MCP_URL` — на MCP Hub / MCP-серверы сервисов Авито; пользователь — токен SSO вместо заголовка от backend.
Агент, права, черновики, интерфейс не меняются.
