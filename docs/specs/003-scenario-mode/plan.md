# 003 — Сценарный режим: план реализации

## 1. Подход
Новый провайдер модели `backend/app/llm/scenario_provider.py` с тем же интерфейсом `LLMProvider`, что у
GigaChat и OpenAI-совместимых сервисов. Агент не знает, что модель «ненастоящая»: тот же цикл инструментов,
те же права и черновики. Провайдер — детерминированный разбор намерения по ключевым словам + сборка ответа
из результатов инструментов и фрагментов документов, которые агент уже кладёт в системное сообщение.
Поэтому сценарный режим доказывает, что механика (права, черновик → подтверждение, отказ) работает
независимо от модели.

## 2. Что меняется
| Часть | Файлы | Зона |
|---|---|---|
| Провайдер | `backend/app/llm/scenario_provider.py`, `backend/app/llm/__init__.py` | Claude |
| Настройки | `backend/.env.example`, `README.md` | Claude |
| Интерфейс | `frontend/src/app/page.tsx` (режим `scenario` = сценарные объяснения) | Claude |

## 3. Данные и контракты
- `LLM_PROVIDER`: `gigachat` | `openai` | `scenario` (по умолчанию без ключа) | `echo` (разработка).
- `GET /health` → `llm_provider: "scenario"` — интерфейс показывает «сценарный режим».
- Документы в системном сообщении агента: блоки `### <title>\n<content>` после строки
  «Контекст из документов команды» (формат задаёт `app/agent/service.py`). Релевантность — пересечение
  основ слов вопроса и фрагмента (поиск RAG без ключа всегда отдаёт top-k, порога у него нет).

## 4. Проверка
Юнит-тесты провайдера на каждый AC + сквозные тесты через `/chat` с `LLM_PROVIDER=scenario`
(черновик создан, заявка не создана; отказ на чужой план).

## 5. Риски и запасной вариант
Ключевые слова не покрывают все формулировки → на непонятный вопрос режим отвечает по документам или
честно «в базе нет» с черновиком вопроса. Это поведение спеки, а не сбой.

## 6. Что заменяется при внедрении в Авито
Ничего: в Авито работает A-Vibe через OpenAI-совместимый провайдер; сценарный режим остаётся резервом без сети.
