# Карта интеграции: как забрать AI-buddy в Авито, не переписывая код

Вопрос эксперта на чекпоинте 2: «вы стартап, мы хотим забрать ваш проект — что вы можете сделать, чтобы его перетянуть
без переписывания кода? Нужно показать, что решение интегрируется». Ответ: каждая внешняя зависимость спрятана за одним
интерфейсом. При внедрении меняется реализация за интерфейсом или одна переменная окружения, а агент, правила, права,
интерфейс и тесты остаются как есть.

## Что заменить

| Сейчас в прототипе | В Авито | Что поменять | Где |
|---|---|---|---|
| Вход «Войти как» (заголовок `X-User-Id`) | Корпоративный SSO (OIDC) | Одна функция: пользователь берётся из токена SSO, а не из заголовка | `app/agent/users.py::get_user`, `app/main.py::load_user` |
| Роли и права (`ROLE_PERMISSIONS`) | Ролевая модель Авито | Таблица «роль → права»; проверки в коде не меняются | `app/agent/users.py` |
| Имитации сервисов: план, доступы, найм, отсутствия, напоминания | MCP-серверы сервисов Авито за MCP Hub | Агент уже ходит к ним **по протоколу MCP по сети**. Указать адрес и ключ: `MCP_URL`, `MCP_SERVICE_TOKEN`. Имена и поля инструментов — контракт | `app/agent/services.py` (шлюз), `app/mcp_server/` (контракт, спека 005) |
| GigaChat | A-Vibe или другая внутренняя модель | `LLM_PROVIDER` + ключ; для OpenAI-совместимого API — `OPENAI_BASE_URL`. Новый провайдер — один класс | `app/llm/base.py::LLMProvider` |
| Демо-документы + поиск по словам | Confluence + корпоративный поиск / эмбеддинги | Загрузчик документов из Confluence; эмбеддинги — `EMBEDDINGS_PROVIDER`. Правило «свой документ или общий» уже в поиске | `app/rag/` (`DocumentStore`, `Embedder`) |
| Таблица событий → Grafana; те же события — в Apache Kafka, топик `ai-buddy.events` (служба `kafka` в Docker) | Clickstream / Kafka → ClickHouse | Адрес брокера `KAFKA_BOOTSTRAP` и имя топика `KAFKA_TOPIC`; формат сообщения — одна функция `to_message`. События без текстов вопросов | `app/event_stream.py`, `app/agent/analytics.py`, спека 304 |
| Feature flags: `app/features.py`, значения на ходу в Redis | Система feature flags Авито (compile-time и runtime) | Одна функция `features.enabled(name)`; места проверки в коде не меняются | `app/features.py`, спека 006 |
| PostgreSQL в Docker / Supabase | PostgreSQL PaaS Авито | `DATABASE_URL`; схема — SQL-миграции | `supabase/migrations/` |
| Веб-чат | Mattermost | Уже есть вход для бота (ниже) | `app/integrations.py` |
| Карта навыков в seed | Система найма | Уже есть вход для события «стажёр нанят» (ниже) | `app/integrations.py` |
| `docker compose` | Kubernetes | Готовые образы: backend, mcp, frontend; настройки только через переменные окружения, healthcheck есть | `docker-compose.yml`, `*/Dockerfile` |

## Входы для систем Авито («доступы на внешку»)

Все адреса описаны в **OpenAPI 3.1**: `GET /openapi.json`, страница Swagger UI — `GET /docs`. Описание собирается из
кода, поэтому не расходится с ним (тест проверяет, что описан каждый адрес). Его можно импортировать в API-шлюз,
Postman или сгенерировать по нему клиента.

### Система найма → `POST /integrations/hired`

Учётка стажёра приходит из корпоративного каталога. Система найма присылает итоги собеседования, а бот сам
пересобирает персональную часть плана. Общие пункты, закрытые и добавленные наставником вручную остаются. Стажёр
получает уведомление «План обновлён по итогам собеседования».

```bash
curl -X POST http://localhost:8000/integrations/hired \
  -H "Authorization: Bearer local-docker-demo" -H "Content-Type: application/json" \
  -d '{"intern_id":"intern-liza","skills":{"sql":"novice","testing":"novice","git":"confident"},"growth":["SQL"]}'
```

Ответ: `{"added": ["Практикум: SQL", "Практикум: Тестирование"], "removed": ["Практикум: Git"], ...}`. Ключ службы —
`INTEGRATION_TOKEN` (в Docker — `local-docker-demo`, на стенде задайте свой). Пустой ключ выключает вход (503).

### Mattermost → `POST /integrations/mattermost`

Отвечает тот же агент, что и в веб-чате: с теми же правами, документами и черновиками. Черновик подтверждается в
AI-buddy, из мессенджера ничего не отправляется без подтверждения. Ответ видит только автор.

Подключение в Mattermost: **Интеграции → Slash-команды → Добавить** (или «Исходящие вебхуки»):
1. Команда `/buddy`, адрес запроса `https://<стенд>/integrations/mattermost`, метод POST.
2. Токен, который выдаст Mattermost, записать в `MATTERMOST_TOKEN`.
3. Если логины Mattermost не совпадают с id в каталоге — `MATTERMOST_USERS="anya.smirnova=intern-anya,…"`.

Проверить без Mattermost (так же шлёт запрос сам Mattermost):

```bash
curl -X POST http://localhost:8000/integrations/mattermost \
  -d "token=local-docker-demo" -d "user_name=intern-anya" -d "text=что мне делать дальше?"
```

## Что уже готово к переносу

- **Контракты, а не код**: агент знает инструменты сервисов по MCP-описанию, фронт — API по OpenAPI. Замена сервиса не
  требует правки агента.
- **Права проверяет сервер, а не модель**: при подключении к реальным сервисам утечки через «хитрый вопрос» нет.
- **Любое изменение — черновик и подтверждение человеком** (кроме простого доступа по кнопке, SPEC 3.5).
- **Персональные данные**: в события не пишутся тексты вопросов, причина отгула видна только руководителю, ответы
  наставника публикуются без имён и контактов.
- **Проверка качества переносится вместе с кодом**: золотой набор (`backend/golden`) запускается на любой модели одной
  командой. Так при смене модели видно, не стало ли хуже.
