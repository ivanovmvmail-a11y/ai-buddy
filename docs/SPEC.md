Это продуктовая спецификация всего прототипа. Подробные спецификации отдельных AI-функций (SDD) лежат в
[`docs/specs/`](specs/README.md) и пишутся по этому документу.

## 1. Что мы делаем

**AI-buddy** — помощник стажёра Авито на первые недели. Он знает личный план стажёра, сам подсказывает следующий шаг,
объясняет каждый пункт по документам команды под уровень стажёра и выполняет рутинное действие — заявку на доступ —
через корпоративный сервис, после подтверждения человеком.

**Заявляем один глубоко проработанный сценарий: «Первые недели и чек-лист стажёра».** ТЗ это разрешает
(«3–5 сценариев либо один глубоко проработанный»), а количество сценариев на оценку не влияет: важно, чтобы всё
заявленное работало.

**Дополнение 11.11 (чекпоинт 1).** Эксперт одобрил персонализацию по навыкам («покажите, как это выглядит») и
проактивность. Поэтому основной сценарий углубляем: план = общие пункты для всех + персональные пункты по карте навыков
(3.1), бот предлагает наставнику поднять уровень (4). Вторым, коротким сценарием заявляем **отгул на один день**
(3.8): бот сам узнаёт ситуацию по фразе в чате и предлагает черновик заявления — это то же «черновик → подтверждение»,
что и у заявки на доступ.

**Гипотеза.** Если стажёр в первые недели видит свой план, получает объяснения под свой уровень и может оформить
доступ, не разыскивая инструкцию и ответственного, то пункты первых недель закрываются быстрее, а до наставника
доходит меньше рутинных вопросов.

**Позиционирование.** Не отдельная платформа, а доменный агент онбординга для ИИ-экосистемы Авито: действия — через
MCP, модель переключается (GigaChat в демо, A-Vibe при внедрении), события уходят в аналитику, вход и роли — корпоративные.

## 2. Пользователи и роли

Вход в прототипе — экран «Войти как…» со списком тестовых пользователей, без паролей (в Авито — корпоративный SSO).

| Роль | Что делает в сценарии |
|---|---|
| **Стажёр** (основной) | Видит свой план и профиль, спрашивает бота, подтверждает заявки, отмечает свои пункты |
| **Наставник** | Видит карточки своих стажёров, отмечает свои пункты плана, одобряет заявку в пространство команды, правит карту навыков |
| Руководитель | Чтение: прогресс стажёров своей команды; отмечает единственный свой пункт плана — «цели обсуждены»; с 11.11 — согласует или отклоняет заявки на отгул своих стажёров (3.8) |
| Куратор | Только чтение: прогресс всех стажёров, **без карты навыков** |
| HR BP | Обычный чат, без доступа к планам и профилям |

Демо-пользователи: стажёры Аня и Кирилл (наставник Пётр, «Платформа объявлений»), Иван и Лиза (наставник Мария,
«Авито Доставка»; Кирилл и Лиза добавлены 11.11 для экрана сравнения, 3.1).

Руководитель, куратор и HR BP новых экранов не получают: они нужны, чтобы показать разграничение прав.
Исключение с 11.11: у руководителя на его экране — список заявок на отгул с кнопками решения (3.8).

## 3. Сценарий «Первые недели и чек-лист стажёра»

### 3.1. План
- Источник — чек-лист стажёра Авито, **пересказанный своими словами** со ссылкой на оригинал (дословно не копируем).
- **Недели 1–2 работают полностью.** Этапы «Месяц 1», «Месяц 2», «После 3 месяцев» показаны контуром «впереди», без действий.
- У каждого пункта есть: название, этап, **ответственный** (стажёр или наставник), тема (для связи с картой навыков),
  связанный документ, связанный сервис (если есть), срок в днях от старта.
- **Общий каркас + пункты команды.** Общие пункты одинаковы у всех; у каждой команды 2–3 своих
  (своё пространство, песочница, каналы). Аня («Платформа объявлений») и Иван («Авито Доставка») видят разные планы.
- Пункты наставника (добавить в чаты, назначить 1:1, обсудить цели) видны стажёру; отмечает их наставник под своей ролью.
- **Общие и персональные пункты (решение 11.11).** Эксперт: задачи, общие для всех стажёров, не персонализируются.
  Поэтому у пункта есть **тип**:
  - **общий** — одинаковый у всех стажёров команды (каркас + пункты команды выше), метка «для всех»;
  - **персональный** — 2–3 учебных пункта на стажёра по **слабым темам** карты навыков (`новичок`), метка «для тебя».
- **Каталог персональных пунктов.** Готовый список «тема + уровень → пункт с документом»: 4–5 тем на команду, по одному
  учебному пункту на тему; темы — из существующей карты навыков (Git, SQL, CI и т. п.). Каталог работает **без ключа ИИ**,
  результат одинаков при каждом запуске — ИИ пункты не придумывает.
- **Подпись «почему».** У персонального пункта видна причина: «в карте навыков Git — новичок». Без слова «слабость» —
  только факт из карты (раздел 4).
- **Сильная тема.** Если стажёр в теме `уверенно`, общий пункт по этой теме **остаётся обязательным**: получает метку
  «ты это умеешь — коротко» и сжатое объяснение (3.4). Пропустить общий пункт нельзя.
- **Пересборка при смене уровня.** Уровень вырос → незакрытый персональный пункт по теме снимается; закрытые пункты
  не трогаем (история сохраняется). Уровень снизился до `новичок` → пункт из каталога добавляется.
- **Наставник правит персональные пункты** на своём экране: убрать персональный пункт или добавить из каталога. Общие
  пункты он не убирает. Если не успеваем — эту правку режем первой (13): наставник и так влияет на план через уровень.
- **Как видна разница.** Решение Миши 11.11: в каждой команде **по два стажёра** у одного наставника, с
  противоположными картами навыков. «Платформа объявлений», наставник Пётр: Аня (Git — новичок, SQL — уверенно) и
  **Кирилл** (Git — уверенно, SQL — новичок). «Авито Доставка», наставник Мария: Иван (Git — уверенно, SQL — новичок) и
  **Лиза** (Git — новичок, SQL — уверенно). Внутри команды все общие пункты одинаковые, персональные разные:
  у Ани «для тебя» по Git, у Кирилла — по SQL. Наставник видит это рядом на экране сравнения (5). Две команды
  остаются: на них показываем, что у каждой свой план, свой каталог и свои документы, а чужое не видно.
- **Лестница этапов.** Над планом — путь стажёра ступенями по этапам плана: «Недели 1–2» → «Месяц 1» → «Месяц 2» →
  «После 3 месяцев» (дальние ступени — контуром, как и сами этапы). Видно, на какой ступени стажёр сейчас и сколько пунктов осталось до следующей. Это личный прогресс:
  без баллов, без сравнения с другими стажёрами.

Примерный состав недель 1–2 (уточняется в спецификации 101):

| Этап | Пункт | Ответственный | Сервис |
|---|---|---|---|
| Неделя 1 | Познакомиться с командой | стажёр | — |
| Неделя 1 | Запросить базовые доступы (трекер задач, база знаний) | стажёр | доступы, выдаются автоматически |
| Неделя 1 | Запросить доступ в пространство команды и изучить его | стажёр | доступы, одобряет наставник |
| Неделя 1 | Добавить стажёра в чаты и каналы | наставник | — |
| Неделя 1 | Назначить регулярные 1:1 | наставник | — |
| Неделя 1 | Обсудить цели, план адаптации и критерии успеха (по ответу организаторов — с руководителем) | руководитель | — |
| Неделя 1 | Завести конспект встреч с наставником | стажёр | — |
| Неделя 1 | Пункты команды (например, поднять песочницу) | стажёр | — |
| Неделя 2 | Получить у куратора инструмент отслеживания прогресса, внести цели | стажёр | — |
| Неделя 2 | Изучить документы и мануалы команды | стажёр | — |

### 3.2. Статусы и «следующий шаг»
Статусы пункта: `не начат` · `в работе` · `ждёт другого человека` · `сделано` · `просрочен` (вычисляется по сроку).

- **Автоматически по событию сервиса:** заявка создана → `ждёт другого человека`; сервис вернул «доступ выдан» → `сделано`.
- **Вручную:** пункты без сервиса отмечает ответственный (стажёр — свои, наставник — свои). Наставник может вернуть пункт стажёра.
- **Следующий шаг** — первый незакрытый пункт текущего или просроченного этапа, где ответственный — текущий пользователь.
  Если все такие пункты ждут других людей, бот показывает, кого ждём и сколько дней.

**Итоги недели.** Раз в неделю (в демо — по кнопке «Следующий день» при переходе через конец недели) бот собирает
стажёру короткую сводку по фактам из событий: какие пункты закрыты, какие доступы получены, что переходит на
следующую неделю. Только факты — качество работы бот не оценивает и баллов не ставит. Ту же сводку видит наставник
в карточке стажёра: это готовая основа для встречи 1:1.

### 3.3. Бот ведёт сам
При входе бот первым пишет короткое сообщение: какой сегодня день стажировки, что закрыто, какой следующий шаг,
и кнопку действия, если оно есть («Сделать за меня»). Тон — на «ты», дружелюбно, как коллега.

### 3.4. Объяснение пункта
Клик по пункту плана (или вопрос в чате) → бот объясняет, зачем пункт нужен, как его выполнить и к кому идти.
Ответ строится по документам, доступным пользователю, **со ссылкой на источник** и пометкой «демо-данные, не регламент Авито».
В конце ответа бот сам предлагает 2–3 уточняющих вопроса кнопками («Как выглядит заявка?», «К кому идти, если не выдали?»),
чтобы стажёру не приходилось придумывать вопросы самому.

По пункту с меткой «ты это умеешь — коротко» (сильная тема, 3.1) объяснение **сжатое**: суть в 1–2 предложениях и
ссылка на документ; кнопка «Подробнее» даёт полный вариант. Пункт при этом остаётся обязательным.

**Задание на практике.** Эксперт на вебинаре 10.11 прямо сказал: «привязать к чек-листу модель, чтобы отвечала на
вопросы, мы и сами можем». Поэтому у пунктов, где это уместно, бот даёт не только объяснение, но и короткое
практическое задание из тестовых данных команды (пример эксперта: не «получи доступ к Grafana», а «открой Grafana,
найди два дашборда, посмотри время ответа сервиса»). Задание — подсказка, а не проверка: бот его не оценивает.

Тестовые документы команд отвечают прежде всего на вопросы «как» вокруг разработки — именно их, по словам эксперта,
стажёры чаще всего несут наставнику: как забрать репозиторий, куда отправить pull request, кого звать на ревью,
что делать с красным пайплайном, как запустить сервис, где посмотреть свои задачи и план развития.

Поиск должен надёжно находить фамилии в любом падеже, номера заявок и названия сервисов; контакты («кто отвечает за…»)
бот берёт из справочника людей команды, а не из текста документов. Качество проверяется золотым набором (раздел 10).

### 3.5. Действие: заявка на доступ
Организаторы на Q&A подтвердили: отдельная имитация сервиса доступов допустима.

1. Стажёр нажимает «Сделать за меня» или просит в чате.
2. Бот готовит **черновик** заявки и показывает карточку с полями, которые назвали организаторы: ресурс (проект
   или пространство), обоснование, уровень прав (чтение / редактирование / администрирование; стажёру бот
   предлагает минимально достаточный — чтение), кто согласует.
3. Стажёр нажимает «Подтвердить» (или «Отменить»). Без подтверждения ничего не выполняется.
4. Имитация сервиса возвращает номер заявки и статус. Бот показывает результат, он сохраняется в базе и виден в плане.
5. Дальше два пути:
   - **базовые доступы** (трекер, база знаний) сервис выдаёт сам → пункт `сделано`;
   - **пространство команды** одобряет человек — владелец ресурса. В тестовых данных это наставник: под своей
     ролью он видит заявку и нажимает «Одобрить» или «Отклонить» → пункт стажёра `сделано` либо возвращается
     с причиной. Стажёр одобрить заявку не может.

По ответу организаторов согласующий в Авито зависит от типа ресурса (владелец проекта, руководитель, DevOps),
поэтому согласующий — поле ресурса в имитации сервиса, а не жёсткое правило в коде. Статусы заявки моделируем сами:
`создана` → `на согласовании` → `выдан` / `отклонена`.

Эксперт на вебинаре: отдельный портал заявок разрабатывать **не нужно** («вы уводите решение кейса в удобное вам
русло»), достаточно адаптера с описанным контрактом или MCP-сервера. Поэтому имитация — тонкая: MCP-инструменты
и данные, без собственного интерфейса; одобрение — одна кнопка на экране наставника. Набор полей заявки —
настраиваемый список у типа ресурса (в командах Авито поля бывают свои), а не жёстко заданная форма.

### 3.6. Напоминания и ход времени
- Имитация ИИ-крона раз в «день» проверяет планы и создаёт напоминания: «заявка ждёт 2 дня — напомнить наставнику?»,
  «пункт недели 1 просрочен».
- Напоминание — **одно на зависший пункт**, с кнопками «Сделать сейчас» / «Напомнить позже». Без повторов и упрёков.
  Показывается в интерфейсе (колокольчик и сообщение бота).
- Для демо: у стажёров **разные стартовые состояния** (Аня — день 2, Иван — день 8 с просроченным пунктом) и кнопка
  **«Следующий день»** в демо-панели, явно помеченной как инструмент демонстрации.

**Новые напоминания и единые уведомления (решение 11.11).** Миша: уведомления и напоминания — обязательная часть
интерфейса, их не режем. Все новые события приходят через **уже существующие** колокольчик и сообщения бота, в одном
стиле: короткий текст + **одно действие-кнопка** (открыть пункт, решить, напомнить). Не больше одного напоминания на
один повод, без повторов и упрёков.

| Кому | Повод | Текст (пример) | Кнопка |
|---|---|---|---|
| Стажёру | Наставник поднял уровень | «Наставник отметил: Git — уверенно. План обновился» | Открыть план |
| Стажёру | В план добавлен персональный пункт | «В план добавлен пункт для тебя: … (в карте навыков Git — новичок)» | Открыть пункт |
| Стажёру | Заявка на отгул ждёт решения 2 дня | «Заявка на отгул ждёт 2 дня — напомнить руководителю?» | Напомнить |
| Стажёру | Решение по отгулу | «Отгул на 14.11 согласован» / «…отклонён» | Открыть |
| Стажёру | День отгула | «Сегодня ты отсутствуешь, сроки пунктов сдвинуты» | Открыть план |
| Наставнику | Бот предлагает поднять уровень | «Бот предлагает поднять уровень: Аня, Git (закрыла 2 пункта)» | Решить |
| Наставнику | Согласованный отгул стажёра | «Аня отсутствует 14.11» (без причины) | — |
| Руководителю | Новая заявка на отгул | «Новая заявка на отгул от Ани на 14.11» | Решить |

Кнопки (решение Миши 12.11, после независимой проверки): у факта — одна «Открыть», после неё уведомление уходит;
у того, что ждёт действия, — главная кнопка и тихая ссылка «Напомнить завтра». Кнопки «Готово» нет: уведомление уходит
само, когда дело сделано.

Сдвиг сроков пунктов в день отгула — желательно; если не успеваем, режем вторым после ручной правки пунктов (13).
Отклонённое предложение по уровню стажёру **не показывается** (раздел 4).

### 3.7. Если ответа нет в документах
Бот не выдумывает. Он говорит, что в базе этого нет, называет, кто скорее всего знает, и показывает
**черновик вопроса с контекстом**, который стажёр копирует сам. Отправки сообщений и входящих в заявленном сценарии нет.

Порядок «к кому идти» — по ответу эксперта: наставник → руководитель → HR BP. Организационные вопросы (отпуск,
документы, компенсации, обучение) — сразу к HR BP: инженер на них не отвечает.

**Если документы противоречат друг другу** (общая инструкция и инструкция команды говорят разное), бот не выбирает
молча: показывает оба варианта с источниками, говорит, что они расходятся, и советует уточнить у наставника.
Событие «противоречие в документах» попадает наставнику в «Частые темы» (раздел 5) — это сигнал обновить документ.

### 3.8. Второй сценарий: отгул на один день (решение 11.11)
Раньше был бонусом (раздел 11); после чекпоинта 1 заявляем как короткий второй сценарий — он показывает проактивность,
которую одобрил эксперт. Основа — имитация сервиса отсутствий Codex (PR #46, `backend/app/mcp_server/ABSENCE.md`).

1. Стажёр пишет в чат «мне завтра к врачу» или «как отпроситься?». Бот узнаёт намерение «отгул» (и без ключа ИИ — по
   словам) и отвечает **по регламенту** из документов с источником.
2. Под ответом бот **сам** предлагает кнопку «Подготовить заявление».
3. Черновик: дата (один день, не раньше сегодняшнего дня стажировки), причина из **закрытого списка** — личные, семейные
   или учебные дела, руководитель (из профиля стажёра). Свободного текста причины и медицинских полей нет: слово «врач»
   из чата в заявку не попадает, бот предлагает «личные дела».
4. Стажёр проверяет и нажимает «Подтвердить» → заявка уходит **руководителю**. Без подтверждения ничего не отправляется.
5. Руководитель на своём экране нажимает «Согласовать» или «Отклонить». После отказа стажёр может подать заявку на этот
   день снова.
6. Наставник видит только факт «Аня отсутствует 14.11» — без причины и истории заявок.
7. Напоминания (3.6): «заявка ждёт решения 2 дня — напомнить руководителю?»; решение по заявке; в день отгула —
   «сегодня ты отсутствуешь, сроки пунктов сдвинуты» (сдвиг сроков — желательно).

Больничный, отпуск и кадровые вопросы — не этот сервис: бот, как и раньше, направляет к HR BP (3.7).

## 4. Профиль стажёра и карта навыков

Отличительная черта: бот учитывает уровень стажёра.

- **Карта навыков по темам**, без баллов и общей оценки: например, «Git — новичок», «SQL — уверенно»,
  плюс сильные стороны и темы для роста. Уровни: `новичок` · `знаком` · `уверенно`.
- **Источник** — имитация сервиса «Найм» (есть в перечне сервисов ТЗ), читается через MCP. При внедрении данные
  остаются в системах Авито, бот их только читает.
- **Баллы отбора, видео и их анализ не храним и не показываем.**
- **Стажёр видит** всё, что бот о нём знает (страница «Мой профиль»), но не правит.
- **Правит только наставник.** ИИ уровень сам не меняет — никакой автоматической оценки человека.

**Профиль обновляется по делам стажёра (решение 11.11): бот предлагает — наставник решает.**
- Поводы для предложения: стажёр закрыл пункты по теме (например, 2 пункта по Git); стажёр отметил у пункта
  «это я уже знаю».
- Наставник видит предложение с основанием («закрыла 2 пункта по Git») и кнопки «Поднять уровень» / «Оставить».
  Решение — всегда за наставником; бот уровень сам не меняет.
- Стажёр видит **только результат**: «Наставник отметил: Git — уверенно», и план пересобирается (3.1). Само
  предложение и отклонённые предложения стажёру не показываются — бот не выносит ему оценок.
- Бот не участвует в решениях о судьбе стажёра — это продуктовое правило команды.

На что влияет профиль:

| Где | Как |
|---|---|
| Глубина объяснения | Новичку в теме — по шагам с примером; уверенному — коротко со ссылкой. Демо: Аня и Иван задают один вопрос, ответы разные |
| Подсказки в плане | У пункта по слабой теме — пометка «здесь помогу подробно» и ссылка на гайд для начинающих; по сильной — «ты это знаешь». ~~Порядок пунктов не меняется~~ — заменено 11.11 строкой ниже |
| Состав плана (11.11) | Общие пункты одинаковы у всех и не меняются; по теме `новичок` добавляется 2–3 персональных пункта из каталога с подписью «почему»; по теме `уверенно` общий пункт остаётся обязательным с меткой «ты это умеешь — коротко». Уровень вырос → незакрытый персональный пункт снимается, закрытые остаются (3.1) |
| Сводка наставника | Наставник видит сильные стороны и темы для роста |

На что профиль **не влияет**: права и доступы, тон, любые решения о человеке. Бот никогда не говорит стажёру про его «слабость».

## 6. Интерфейс

- Главный экран: **план слева, чат справа**. Клик по пункту открывает объяснение в чате; действие в чате сразу меняет
  статус в плане. На узком экране — переключение «План / Чат».
- Карточка черновика с кнопками «Подтвердить» / «Отменить», затем результат и номер заявки.
- Под ответом бота — источники и кнопки «полезно / не полезно».
- Страницы: «Мой профиль», экран «Войти как…», колокольчик напоминаний, демо-панель («Следующий день», режим модели).
- Требования ТЗ: простые действия — быстрее 1 секунды; обращение к модели не блокирует интерфейс, виден статус
  ожидания; при сбое — понятное сообщение и возможность повторить.
- Стек: Next.js (React) + TypeScript; данные с сервера — TanStack Query, состояние — Zustand, проверка данных — Zod
  (стек Авито из ТЗ). Тесты — Vitest.

## 7. Права и безопасность

- Права проверяются на сервере перед каждым вызовом инструмента (роль + доступ к конкретным данным); модель не
  считается границей безопасности. MCP-сервер проверяет права сам.
- Недоступные сведения не раскрываются, в том числе сам факт их существования.
- Любое изменение — только черновик → подтверждение человеком → результат сохраняется.
- Текст документов — данные, а не команды: инструкция внутри документа действие не запускает.

## 8. Работа без ключа и с ключом

- **С ключом** (GigaChat или любой OpenAI-совместимый сервис, включая A-Vibe) работает настоящая модель.
  README описывает сервис, модель, переменную окружения и пример конфигурации без секретов.
- **Без ключа** включается **сценарный режим**: основной путь из README проходится полностью (приветствие, план,
  объяснение пункта в двух вариантах глубины, заявка, одобрение, напоминание, отказ). На произвольный вопрос бот
  показывает найденный фрагмент документа с источником. Режим честно подписан в интерфейсе.
- **Поиск по документам** тоже в двух режимах: с ключом и оплаченными эмбеддингами GigaChat
  (`EMBEDDINGS_PROVIDER=gigachat`) — поиск по смыслу плюс по словам; без ключа — только по словам. Оба режима
  проверяются золотым набором. Векторы разных режимов не смешиваются: при смене режима документы переиндексируются.
- **Ключ эксперта.** Организаторы сказали: ключ им передавать не нужно, они создадут свой — от нас требуются
  название сервиса и подробная инструкция подключения в README. ~~Их ключ GigaChat~~ Уточнено 12.11 по расшифровке
  Q&A: провайдера выбираем **мы** («укажите, какой нужен провайдер, мы под вас подстроимся»), зарубежные LLM API —
  не минус; GigaChat — наш выбор, а не условие организаторов. Ключ эксперта может оказаться без оплаченных
  эмбеддингов, поэтому при отказе сервиса эмбеддингов поиск **сам переходит на режим «по словам»** и пишет об этом
  в лог, а не падает.
- Основной запуск — `docker compose up`. Проверку Docker выполняет CI на GitHub. Эксперты запускают Docker у себя,
  видеокарты у них нет, интернет при запуске есть.

## 9. Архитектура

```
Интерфейс (Next.js) → API (Flask) → Агент (права, черновики, цикл инструментов)
                                      ├─ модель: GigaChat | OpenAI-совместимая | сценарная
                                      ├─ поиск по документам (PostgreSQL + pgvector, фильтр по правам)
                                      └─ MCP-сервер с имитациями сервисов Авито:
                                           чек-лист новичка · доступы · найм (профиль) · ИИ-крон
PostgreSQL: документы, планы и статусы, заявки и действия, профили, переписка, события
События → таблица в формате Clickstream → Grafana (панель метрик)
```

- **Хранение.** Действия, заявки, статусы плана, переписка и напоминания хранятся в PostgreSQL и переживают
  перезапуск. Переписка и черновики действий — таблицы `chat_messages` и `agent_actions` (13.11, `app/db/history.py`,
  `app/db/actions.py`); подтверждение черновика атомарно одной командой SQL.
- **События.** Вопрос, ответ с источником, отказ, черновик, подтверждение, результат действия, закрытие пункта,
  оценка ответа. Kafka в прототипе нет: показываем на схеме внедрения как замену одного адаптера.
- **Что заменяется при внедрении:** вход и роли → SSO Авито; имитации сервисов → настоящие MCP; модель → A-Vibe;
  расписание → ИИ-крон; события → Clickstream/Kafka.

## 10. Метрики

| Уровень | Что | Как показываем |
|---|---|---|
| Доказываем в прототипе | Точность поиска, доля ответов с источником, правильные отказы | **Золотой набор** из 30–40 вопросов (включая «ловушки»: чужая команда, нет в базе); скрипт и отчёт в репозитории |
| Видим вживую | Вопросы, закрытые без человека; закрытые пункты недели 1; время до ответа; оценки «полезно / не полезно» | Панель Grafana по событиям |
| Гипотеза для пилота | Часы наставника в неделю (сейчас ~5 ч первые 2–3 месяца), удовлетворённость чек-листом (сейчас 68%), дни до первой самостоятельной задачи (сейчас ~2 недели), длительность адаптации (сейчас ~2 месяца) | План пилота: две группы одного потока стажёров (с ботом и без); опрос и учёт часов наставника в конце недели 2 и месяца 2 |

**Базовые цифры от организаторов (12.11, приблизительно, только по стажёрам):** удовлетворённость онбордингом 9/10,
чек-листом — 68%, наставником — 90%; до первой самостоятельной задачи ~2 недели, адаптация ~2 месяца; наставник —
~5 ч/неделю первые 2–3 месяца (доступы, задачи, погружение, 1:1), после — 2–3 ч/неделю. Частые вопросы: организационные
(доступы, оборудование, документы), по задачам (формулировка, ревью, приоритизация), профессиональные (инструменты),
развитие (ИПР, матрица компетенций), обратная связь. Стажёр получает те же доступы, что и команда (Jira, Confluence,
Redash, Grafana, Stash). Под эти вопросы добавлены демо-документы «Рабочее оборудование стажёра» и «Как
приоритизировать задачи».

Проценты эффекта из маркетинговых источников не называем. Золотой набор строим от типичных вопросов, которые назвал
эксперт на вебинаре (репозиторий, pull request, ревью, окружение, задачи, план развития, доступы, ноутбук, отгул).
План пилота оформляем как A/B-проверку: эксперт подтвердил, что метрики и способ проверки команда выбирает сама,
но они должны быть.

- **Изменение 11.11:** отгул **больше не бонус** — это второй сценарий (3.8), Codex доводит PR #46 из Draft.
  Входящие наставника (PR #45) и PR #50 остаются бонусами в Draft.
- Обсудили и не берём (идеи команды 10.11): рейтинг и соревнование стажёров, баллы за успехи — стажёры в разных
