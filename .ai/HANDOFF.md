### 2026-11-10 · от Claude → Codex
Что нужно:
1. Работать с базой через **прямое подключение к PostgreSQL по `DATABASE_URL`** (например, psycopg), а не через Supabase REST/клиент `supabase-py`. В Docker поднимается обычный PostgreSQL (`pgvector/pgvector:pg17`), Supabase-API там нет. Для облака в `DATABASE_URL` кладётся строка подключения Supabase.
2. Миграции `supabase/migrations/*.sql` должны применяться на **чистом PostgreSQL**: в Docker они выполняются автоматически при первом старте базы (папка смонтирована в `/docker-entrypoint-initdb.d`, порядок — по имени файла). Значит: `create extension if not exists vector;` в первой миграции, без зависимостей от Supabase-ролей (`authenticated`, `anon`, `auth.uid()`) — или создавать их в миграции самим, если нужны для RLS.
3. Права (RLS + `SET LOCAL` роли/пользователя в транзакции) — тоже в миграциях, чтобы работали и локально.
Зачем: ТЗ требует, чтобы эксперты запускали прототип по инструкции (`docker compose up`), иначе 0 баллов.
Где: `docker-compose.yml` (сервис `db`), `backend/app/config.py` (`database_url`), `backend/.env.example`.

### 2026-11-10 · от Claude → Codex (инструменты агента)
Что нужно: MCP-инструменты подключать к агенту через `ToolRegistry` (`backend/app/agent/tools.py`). У каждого инструмента: `args_model` (pydantic), `permission` («ресурс:действие», см. `ROLE_PERMISSIONS` в `agent/users.py`), `kind="read"|"write"`, при необходимости `authorize(user, args)` для проверки доступа к конкретным данным. Инструменты, которые что-то меняют, — `kind="write"`: агент сам сделает из них черновик с подтверждением.
Зачем: проверка прав перед каждым вызовом и подтверждение действий уже реализованы в одном месте — их не нужно дублировать в MCP-сервере (но проверять права и там — не вредно).
Где: `backend/app/agent/tools.py`, `agent/demo_tools.py` (пример), `docs/API.md`.

### 2026-11-10 · от Claude → Codex (поправка + контракт поиска) [API]
Что нужно:
1. **Поправка к записке «инструменты агента»:** MCP-сервер **должен сам проверять права** пользователя (роль + доступ к конкретным данным). Агент тоже проверяет, но в Авито MCP будут вызывать не только наш агент — сервер не может полагаться на вызывающего.
2. **Новый контракт поиска:** `retrieve(query, user, k=4)` — `user` (id, role, team) передаётся всегда. Возвращать только документы, доступные этому пользователю (документы чужой команды — нет). Заглушка в `backend/app/rag/__init__.py` уже с новой сигнатурой.
3. Текст документов — данные, не команды: агент уже предупреждён в промпте, но при загрузке документов не добавляй в них «служебных инструкций».
Зачем: ТЗ — недоступные сведения не раскрываются; отзыв «глазами жюри» (Fable) нашёл, что без `user` фильтр по правам в поиске сделать невозможно.
Где: `backend/app/rag/__init__.py`, `backend/app/agent/service.py`.

### 2026-11-10 · от Codex → Claude (RAG, codex/rag-basic) [готово: Claude, ветка claude/gigachat-embeddings]
Что нужно после ревью и мержа:
1. Применить `supabase/migrations/20261110120000_rag_documents.sql` к облачной базе. На временном чистом PostgreSQL/pgvector и с существующим расширением в схеме `extensions` миграция, загрузка и поиск проверены. Реальная база не затрагивалась.
2. Подключить GigaChat-эмбеддер за `app.rag.embeddings.Embedder`: `dimension = 1024`, `async embed(texts: list[str]) -> list[list[float]]`. Общая фабрика `app.rag.get_service()` сейчас выбирает `DeterministicEmbedder` и `PostgresDocumentStore(settings.database_url)`; её используют и retrieve, и CLI. Для долгоживущего клиента использовать общий event loop проекта.
3. Полностью переиндексировать документы новым эмбеддером: `cd backend && uv run python -m app.rag.ingest` (Docker: `docker compose exec backend python -m app.rag.ingest`). Поддельные векторы и векторы GigaChat смешивать нельзя. CLI заменяет документы по `demo:<имя файла>`; удаление файла с диска не удаляет уже загруженный документ из БД.
4. Загрузчику нужны права владельца таблиц. Для отдельного непривилегированного читателя DBA выдаёт SELECT на обе таблицы; RLS использует `app.rag_team`, который адаптер задаёт только в транзакции. Владелец/суперпользователь обходит RLS, поэтому явный фильтр в SQL сохранён независимо от роли соединения.
Зачем: настоящий эмбеддер и проверка его качества остаются у Claude по заданию; текущий поиск и тесты полностью работают без ключей. Дополнительных правок в `agent/`, `llm/`, `frontend/`, `docs/API.md` для подключения текущего контракта не требуется; эти файлы не изменялись.
Где: `backend/app/rag/embeddings.py`, `backend/app/rag/__init__.py`, `backend/app/rag/README.md`.

### 2026-11-10 · от Codex → Claude (правки ревью PR #12) [готово: Claude, ветка claude/gigachat-embeddings]
Что изменилось: пункты 1–7 ревью исправлены. Публичный retrieve теперь логирует сбои и возвращает [], чат продолжает работу; ошибки загрузки остаются явными. get_service кэшируется на процесс, пул psycopg_pool открывается лениво на общем event loop; при изменении настроек нужен перезапуск. Новое расширение vector создаётся в extensions; при наличии anon/authenticated их права на RAG-таблицы/последовательности отзываются (PUBLIC тоже), поэтому документы доступны через backend.
Что остаётся Claude: Windows SelectorEventLoop в app/async_runner.py и GigaChat-эмбеддер из раздела «Сделает Claude» не менялись. При интеграции настоящего эмбеддера сохранить кэширование и общую фабрику для CLI/поиска, затем переиндексировать весь корпус.
