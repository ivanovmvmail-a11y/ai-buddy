### 2026-11-11 · от Codex → Claude (101-T3: PostgreSQL и запуск)
Готово: PostgresStore, get_store по DATABASE_URL, миграция 20261111010000_onboarding.sql, идемпотентный seed/сброс выбранной БД, авто-seed перед gunicorn в Docker. Новых зависимостей нет. Все общие MCP-тесты проходят на памяти и PostgreSQL (--mcp-postgres); AC-5 закрыт тестом между разными Python-процессами.

Что нужно после мержа: применить миграцию к облачной базе от владельца/доверенного backend-пользователя и выполнить из backend `uv run python -m app.mcp_server.seed` с DATABASE_URL. Docker для нового volume применяет SQL сам; для существующего volume нужна ручная миграция (команда в README модуля), затем перезапуск backend. `--reset` сбрасывает все данные семи таблиц онбординга выбранной БД, это больше не сброс памяти короткого CLI-процесса. `--validate` — прежняя проверка JSON без подключения. При непустой или частично заполненной БД обычный seed сохраняет данные. Недоступная настроенная БД не заменяется памятью.

Права: роли Supabase не создаются/не требуются; RLS включён без клиентских политик, PUBLIC и существующие anon/authenticated лишены прав на таблицы/последовательность событий. Backend подключается как владелец/роль BYPASSRLS. Права конечных пользователей остаются внутри сервисов, прежние проверки всех 8 ролей прошли на PostgreSQL. app/agent/, app/llm/, frontend/, main.py, docs/API.md не менялись.

Пункт 6 ревью #17 реализован: внутренний read(include_events=False) выдаёт отделённые модели без копии полного состояния/журнала; история нужна лишь сводке и list_events. Сервисы используют transaction(include_events=False, copy_on_commit=False) для записи: один доменный снимок в памяти, изменение строк и append событий в PostgreSQL; результаты сервисов отделены. Старый transaction() без флагов сохраняет совместимую полную изоляцию для административных снимков/тестов, а не обычных операций. get_plan по spec продолжает писать два события просмотра, но не читает/копирует/перезаписывает старый журнал. read-view — внутренний Mapping/Sequence, не DTO для сериализации целиком. Общие сигнатуры пользовательских функций не менялись.

Транзакции: запись/seed/reset сериализуются одной advisory-lock БД между процессами (сценарий двух стажёров), чтение использует REPEATABLE READ. Инвариант активной заявки и одного напоминания на пункт дополнительно защищён индексами. Обычная запись не грузит историю и не переписывает её; явный reset заменяет историю в той же транзакции. Для большого реального сервиса блокировки/выборки можно сузить при замене имитаций, сейчас сохраняется интерфейс полного доменного unit of work.

Проверено: --mcp-postgres → 453 passed / 4 skipped, покрытие 98,78%; без флага → 287 passed / 10 skipped, 93,34%. Флаг запускает только свой временный локальный контейнер с уже скачанным образом, не реальную БД; контейнер удаляется после тестов. Покрыты межпроцессное сохранение/seed/reset, SQL-откат после частичной записи, две независимые очереди пула, закрытый публичный доступ и отсутствие deepcopy старых событий при журнале из 10 000 записей.
