Готово: PostgresStore, get_store по DATABASE_URL, миграция 20261111010000_onboarding.sql, идемпотентный seed/сброс выбранной БД, авто-seed перед gunicorn в Docker. Новых зависимостей нет. Что нужно после мержа: применить миграцию к облачной базе от владельца/доверенного backend-пользователя и выполнить из backend `uv run python -m app.mcp_server.seed` с DATABASE_URL. Docker для нового volume применяет SQL сам; для существующего volume нужна ручная миграция (команда в README модуля), затем перезапуск backend. `--reset` сбрасывает все данные семи таблиц онбординга выбранной БД, это больше не сброс памяти короткого CLI-процесса. `--validate` — прежняя проверка JSON без подключения. При непустой или частично заполненной БД обычный seed сохраняет данные. Недоступная настроенная БД не заменяется памятью.

Права: роли Supabase не создаются/не требуются; RLS включён без клиентских политик, PUBLIC и существующие anon/authenticated лишены прав на таблицы/последовательность событий. Backend подключается как владелец/роль BYPASSRLS. Права конечных пользователей остаются внутри сервисов, прежние проверки всех 8 ролей прошли на PostgreSQL. app/agent/, app/llm/, frontend/, main.py, docs/API.md не менялись.

Пункт 6 ревью #17 реализован: внутренний read(include_events=False) выдаёт отделённые модели без копии полного состояния/журнала; история нужна лишь сводке и list_events. Сервисы используют transaction(include_events=False, copy_on_commit=False) для записи: один доменный снимок в памяти, изменение строк и append событий в PostgreSQL; результаты сервисов отделены. Старый transaction() без флагов сохраняет совместимую полную изоляцию для административных снимков/тестов, а не обычных операций. get_plan по spec продолжает писать два события просмотра, но не читает/копирует/перезаписывает старый журнал. read-view — внутренний Mapping/Sequence, не DTO для сериализации целиком. Общие сигнатуры пользовательских функций не менялись.

Транзакции: запись/seed/reset сериализуются одной advisory-lock БД между процессами (сценарий двух стажёров), чтение использует REPEATABLE READ. Инвариант активной заявки и одного напоминания на пункт дополнительно защищён индексами. Обычная запись не грузит историю и не переписывает её; явный reset заменяет историю в той же транзакции. Для большого реального сервиса блокировки/выборки можно сузить при замене имитаций, сейчас сохраняется интерфейс полного доменного unit of work.

Все функции `app.mcp_server.absence` async, `user_id: str` первым аргументом, разрешение DEMO_USERS и проверка прав внутри:
- `draft_absence(user_id, day: date, reason: AbsenceReason) -> ActionDraft`: только стажёр, reason=`personal|family|study` (личные/семейные/учебные дела), день один и не раньше виртуальной даты start_date+current_day−1. Руководитель берётся из lead_id и должен быть руководителем той же команды. `confirm_absence(user_id,draft_id) -> AbsenceRequest`: только автор, повторно проверяет дату, назначение руководителя и отсутствие pending/approved-заявки на этот день. Статус pending, руководитель получает входящую.
- `get_request(user_id,request_id) -> AbsenceRequest`, `list_requests(user_id) -> list[AbsenceRequest]`: полные заявки читают только автор-стажёр и текущий назначенный руководитель его команды. Другим стажёрам/руководителям доступны только свои объекты; наставник/HR/куратор не получают полные заявки, даже «своей» команды.
- `draft_decision(user_id,request_id,approve: bool) -> ActionDraft`: только назначенный руководитель, только pending, approve — строгий bool. `confirm_decision(user_id,draft_id) -> AbsenceRequest`: approved/rejected, decided_day из демо-часов стажёра; автор черновика должен всё ещё иметь права. Повтор одного подтверждения идемпотентен; конкурирующее решение — Conflict. После rejected можно повторно запросить день.
- `list_absence_facts(user_id,intern_id) -> list[AbsenceFact]`: только назначенный наставник своей команды. AbsenceFact содержит **только intern_id и day**, только approved, никаких reason/id заявки/истории pending/rejected. Для экрана формировать «отсутствует YYYY-MM-DD»; не прикреплять полную заявку к этому ответу.

`AbsenceRequest`: id, intern_id, lead_id, team, day(date), reason(закрытый enum), created_day, status(pending|approved|rejected), decided_day(optional). Свободного текста причины, диагноза, периода дат или кадровых данных нет. HR-вопросы, больничный и отпуск по-прежнему направлять HR BP; этот сервис только для однодневного отгула. `AbsenceInput` forbids extra поля. Метки причин: `absence_models.REASONS`.

`ActionDraft`: id/owner_id/action/payload/status(pending|confirmed|cancelled)/result_id; `drafts.get_draft(user_id,draft_id)` и `cancel_draft` — только владельцу. UI показывает сохранённый черновик и отдельно вызывает confirm после явного клика, передавая только draft_id и пользователя из сессии. Если существующий ActionStore исполняет callback после подтверждения, адаптер может подготовить+подтвердить внутри этого доверенного callback, сохраняя draft_id для повторов.
